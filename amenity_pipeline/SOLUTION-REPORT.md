Author: Oscar AF / OpenCode session
Purpose: Explain how we arrived at the current enrichment solution, what was

---

## 1. Executive summary

We built a Google Maps enrichment pipeline for the Whappin Puerto Viejo
directory (738 businesses) in two phases:

1. **Hotel-amenity extraction** (`google-maps-amenities-v2`): captures the
   `img "… available/unavailable"` amenity matrix shown on lodging pages.
   **213 / 367 lodging records** (58%) have this data; the rest genuinely do
   not expose it (verified via signed-in session).

2. **About-attribute extraction** (`google-maps-about-attributes-v1`): captures
   the structured attribute groups on the About tab (Accessibility, Service
   options, Offerings, Payments, Atmosphere, Crowd, Parking, Pets, …). This is
   the high-value data for non-lodging categories. Running over all 726 CIDs now.

The solution required correcting a significant false-amenity problem in the
live site and discovering that Google's data itself is the limiting factor, not
our tooling.

## 2. Context: the existing site and its data problem

Whappin is a static directory generated by `paradisio_app/build.py` from
`pv_master_unified.csv` (737 rows, 34 columns) plus enrichment in
`paradisio_app/data/maps_parsed_v3.json` (715 records from an earlier,
coarse, Spanish OCR-based scrape).

**The false-data problem (discovered during this work):**

- `build.py` had a function `infer_amenities()` that, for any lodging record
  WITHOUT scraped amenity data, **injected statistical defaults**:
  - hotel/hostel → `["Free Wi-Fi", "Gym"]`
  - vacation_rental → `["Free Wi-Fi"]`
- It also fell back to the old OCR enrichment (437 records, all at confidence
  0.7), which is coarse, Spanish, and demonstrably wrong for some businesses
  (e.g. Kaya's Place showed "Gym").
- Net effect: the live site displayed amenities businesses may not actually
  offer. This was **fabricated data presented as fact**.

## 3. Phase 1 — Hotel-amenity pipeline

### 3.1 Original approach
Built from a spec (`docs/newCIDScan.md`): Node/TypeScript + Playwright.
Navigate to `https://www.google.com/maps?cid=<cid>&hl=en`, wait for a place
panel, expand "View more amenities", read `page.getByRole("main").ariaSnapshot()`,
parse `img` accessible names ending in exactly `available`/`unavailable`.

Files: `amenity_pipeline/src/{extract,parse,normalize,identity,input,runner,status,cli}.ts`.

### 3.2 First runs failed for the wrong reasons
- Initial full run: 726 records, but ~70% came back `amenities_not_exposed`.
- We initially mis-attributed this to **Google throttling** (booking/pricing page
  variants, cooldowns, rate backoff). This was WRONG.
- A review (Codex) identified the real bugs:

### 3.3 Root-cause corrections (codex review § the six questions)
1. **`isDegradedPage()` was false.** It treated normal lodging-page features
   (`Check availability`, `Compare prices`, `per night`, `Pricing and
   availability`) as throttle signals and discarded valid data. Successful pages
   (e.g. 3 Bamboo) contain those same markers. **Deleted.**
2. **We required an expander before accepting states.** Many pages expose
   `img "… available"` inline with no "View more" button (Casa Lucas case).
   **Fixed: parse states first, accept inline, expand only if present.**
3. **"Limited view" was misread as failure.** It's nearly universal in anonymous
   sessions and coexists with successful extraction. **Downgraded to metadata**
   (`limitedView: boolean`), not a status.
4. **Non-lodging was run through the hotel-amenity extractor.** Restaurants,
   shops, services don't use that widget. **Added category routing.**
5. **New taxonomy** separating outcomes from page features:
   `success_expanded` / `success_inline` / `amenities_not_applicable` /
   `amenities_not_exposed` / `page_inconclusive` / `business_closed`, plus
   orthogonal `metadata` (limitedView, hasBookingUi, tabs).

### 3.4 Evidence recovery
Because the extractor had thrown away valid inline states during classification,
we wrote `scripts/rebuild_results.ts` to re-parse every saved `.aria.yml`
evidence file. This **recovered 66 previously-lost records**, taking the usable
set from 145 → **213 lodging records** with verified amenities.

### 3.5 Signed-in profile investigation
We hypothesized a throwaway Google sign-in would reveal amenities hidden behind
the anonymous "limited view". Built `--profile <dir>` support. Findings:
- Google blocks sign-in on Playwright's bundled Chromium; **real Chrome
  (`channel: "chrome"`) with automation markers stripped** is required.
- The signed-in session only takes effect in **headed** mode; both legacy and
  new headless drop the authenticated Maps session.
- **Decisive result:** with the profile working, 10 previously "limited-view"
  lodging records all rendered full pages (`limitedView: false`) but **0 of 10
  exposed any amenity states**. The limited view was not hiding amenities; those
  businesses genuinely have none in Google's data.

**Conclusion:** 213/367 lodging (58%) have Google amenity data; the rest don't,
regardless of login state. Anonymous scraping was not the limiting factor.

## 4. False-amenity remediation

Per Codex recommendation, we went "verified-only":
1. Exported the 213 evidence-backed amenity sets to
   `paradisio_app/data/verified_amenities.json` (CID-keyed, with true
   `available`/`unavailable`).
2. Rewired `build.py`: amenities now come **only** from verified data.
   - Deleted `LODGING_AMENITIES` injection entirely.
   - Dropped the OCR-amenity fallback (unverified).
   - Verified names bypass the legacy `normalize_amenities()` OCR filter (which
     was dropping English names like "Free Wi-Fi").
3. Display semantics: only `available: true` renders as chips; `available: false`
   (e.g. "Pool" at 3 Bamboo) is omitted — the site no longer implies a business
   offers something it doesn't.
4. Verified result: **exactly 213 pages** with amenities, **zero** injected
   Gym/Wi-Fi, 54/54 tests pass, source-data + release verifiers PASS.

## 5. Phase 2 — About-attribute extraction

### 5.1 Discovery
The About tab exposes **grouped attribute lists** for non-lodging categories:
`heading [level=2]` + `list/listitem`. Restaurants get the richest set (15
groups: Accessibility, Service options, Highlights, Offerings, Dining options,
Amenities, Atmosphere, Crowd, Planning, Payments, Children, Parking, Pets),
services/shops/tours get smaller subsets. Lists are fully expanded (no expander).

### 5.2 Why a separate mode
- Non-lodging (359 CIDs) has no hotel-amenity matrix; its data lives in About
  attributes (present = true, no "not offered" signal).
- The signed-in profile is **required** (anonymous headless hits a Google
  challenge and can't render About reliably).

### 5.3 Implementation
- `extractAboutAttributesFromPage()`: click About tab, snapshot, parse
  heading+list groups. New statuses: `success_attributes`,
  `attributes_not_exposed`.
- Category routing: `mode="about"` for non-lodging; auto-routed by category.
- Identity matcher got a **lenient mode** for about (any brand-token match),
  because non-lodging detected names add Spanish descriptors
  ("Aloe Boutique" → "Aloe Tienda de ropa", "Automotriz Danny" → "Taller y
  lavacar Danny") — these were false mismatches while data was extracted fine.
- 32-record stratified validation: **29/32 with data (91%)** after the identity
  fix; restaurants 32–58 attributes each.

### 5.4 Gap measurement
Scanning all saved evidence for the known attribute-group vocabulary found
groups in only **56/1520 files (3.7%)** — almost entirely the non-lodging
validation batch. This confirmed the gap: **all 726 records need an about-mode
run** to capture About attributes, including lodging exceptions (some hotels
have a "Crowd" group).

### 5.5 Lodging About-tab finding
Probing confirmed lodging About tabs mostly do **not** expose attribute groups —
they reuse the amenity matrix instead (Cabina Mor's About tab = amenity states,
no groups). So for lodging, amenities was the correct capture; the exceptions
(some hotels with a Crowd group) get caught by the about run.

## 9. Attribute display concern — READ BEFORE VISUAL REVIEW (2026-08-02)

**RESOLVED 2026-08-02** — progressive-disclosure Details section implemented per
the adapted Codex proposal (see `ProposedAmenitiesAttributesCleanup.md` and the
commit for §9's predecessor). Current behavior:
- ≤8 attrs: show all, no disclosure.
- 9–20 attrs: 6-chip summary + "View all N details".
- 21+ attrs: 8-chip summary + "View all N details".
- Expanded view: native `<details>` → quiet grouped lists (2-col desktop).
- Category + attribute-level ranking; within-group dedup + conservative aliases
  (e.g. "Wi-Fi"→"Free Wi-Fi"); provenance "From Google Maps · Captured YYYY-MM".
- List cards unchanged.

The analysis below (from the original concern) is retained for context.

**Deployed state:** About attributes are now live on whappin.com. 345 records
carry attribute groups, and some restaurants show **40–67 chips** spread across
up to 15 groups (Accessibility, Service options, Highlights, Popular for,
Offerings, Dining options, Amenities, Atmosphere, Crowd, Planning, Payments,
Children, Parking, Pets, …). Total captured: **5,748 attribute entries**.

**The concern (owner observation):** this is a LOT of detail and is **flooding
the listing pages**. On a mobile-first directory, a page with 60+ chips reads as
visual noise rather than useful information. The current renderer (`biz_attributes`
in `paradisio_app/build.py`) shows **every** attribute group fully expanded, with
no collapse, truncation, or category-aware prioritization.

This is a **display-layer problem only** — the data model already stores groups
as named, structured fields, so any presentation fix requires no re-extraction.

### What Codex should evaluate (including visual inspection of live pages)

1. **Volume/balance** — is 5,748 attributes across 345 pages the right amount,
   or should we surface less? Compare a high-count restaurant page
   (e.g. El Sol del Caribe, 67 attrs) against a low-count one on both desktop and
   mobile.
2. **Collapse strategy** — reuse the existing Amenities truncation pattern
   ("View all N") vs. per-group collapse vs. a "Details" expander that hides
   everything by default.
3. **Group prioritization** — should we surface only 2–3 most relevant groups
   per category (restaurants: Offerings + Service options + Payments; skip
   Atmosphere/Crowd), and de-emphasize the rest?
4. **Provenance labeling** — should attributes show "From Google" / source
   attribution, per Google's data policies?
5. **List-vs-detail** — should the home/list cards show a few highlights while
   the dedicated business page shows everything?
6. **Interaction cost** — touch targets, accordion behavior, and whether chips
   are even the right component for 60 items (vs. a table or grouped list).
7. **Category-specific ordering/labels** — the current group order is a global
   preference list; per-category order may read better.
8. **Empty/partial states** — how it looks when a page has only 1–2 attributes
   (looks sparse next to a 60-chip neighbor).

Owner has explicitly said **do not change the display yet** — this is a
documentation + review request. Codex should produce its own observations,
ideally backed by visual inspection of the live pages, before we decide on an
approach.
